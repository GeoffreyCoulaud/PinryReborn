# Boards (collections)

Date: 2026-07-20
Status: approved design, pending implementation plan
Depends on: pins (CRUD + soft-delete recycle bin), tags (pin↔tag membership), and the
cursor pagination already shipped. No dependency on the image subsystem.

## 1. Goal

Let a user group their pins into **boards**. A board is a named, describable collection.
A pin belongs to **0..N boards** (optional, many-to-many). Cover the full lifecycle: create,
rename, list, browse a board's pins, edit a pin's membership, and delete with a recycle bin.

Boards are the primary organising concept for the upcoming UI navigation, so this sub-project
is a prerequisite for serious UI/extension work.

## 2. Scope

**In scope:**

- A first-class `Board` domain entity, owner-scoped like pins and tags.
- Board CRUD: create, read (detail + list), update (name/description), soft-delete.
- A recycle bin for boards, mirroring `PinRecycleBin`: list recycled, restore, permanently
  delete, empty.
- The pin↔board membership relation, edited **set-based from the pin side**
  (`PUT /pins/{pinId}/boards`), mirroring the existing `PUT /pins/{pinId}/tags`.
- Browsing a board's pins: `GET /boards/{boardId}/pins`, paginated + sorted, reusing the
  existing cursor + `PinSortStrategy`.
- Exposing a pin's boards on `PinOutputDto`, and a live `pinCount` on the board output.

**Out of scope (deferred):**

- **Visibility / sharing** (public or shared boards). Parked repo-wide; everything here stays
  `@Authenticated` and owner-scoped. See `docs/backlog.md`.
- **Board name uniqueness.** Duplicates are allowed by design (see §3).
- **Cover images** for boards. The UI can derive a cover from the board's pins; not modelled.
- **Ordering pins within a board** manually. Pins are returned by the standard sort strategy,
  not a per-board manual position.
- **Assigning boards at pin-creation time.** `POST /pins` does not take board ids; membership
  is set afterwards via `PUT /pins/{pinId}/boards`, mirroring how tags work today
  (`createPin` posts `tags = emptyList()`).

## 3. Key decisions (rationale captured for the plan)

- **A pin belongs to 0..N boards (many-to-many, optional).** A pin in zero boards is valid.
  Membership is a join relation, not a field on either entity.
- **Board carries `name` + `description`.** A board deserves a line of context; the
  description may be empty. This is richer than `Tag` (name only) but stops short of a cover
  image, which is a UI-derivable concern.
- **No name uniqueness.** Two active boards of the same user may share a name. Enforcing
  uniqueness would add a creation/rename error path and, worse, a restore-time conflict with
  the recycle bin (a recycled "Travel" blocking a new "Travel", then colliding on restore).
  The marginal UI benefit did not justify that complexity; boards are distinguished by id.
- **Deletion is soft, with a recycle bin.** Unlike a tag, a board is potentially costly to
  lose: its value is the set of associations, and rebuilding them by hand is painful. So
  boards mirror the pin recycle-bin pattern (soft-delete → restore / permanently delete /
  empty). Soft-delete **preserves** the `pin_board` rows so a restore is exact; only a
  permanent delete clears them.
- **Membership is edited set-based from the pin side.** `PUT /pins/{pinId}/boards` replaces
  the pin's whole board set, mirroring `PUT /pins/{pinId}/tags`. This reuses a proven,
  fully-covered pattern (`PinTagger`), and naturally serves the extension (fix the boards
  when pinning). Difference from tags: a board is a first-class entity that must pre-exist, so
  the body carries **board ids** (UUIDs), not names.
- **Board listing is a simple unpaginated list.** A user has at most a few dozen boards;
  `GET /boards` returns them all (active only), sorted by `name` (case-insensitive) with `id`
  as a deterministic tie-breaker (there is no `createdAt` on the entity, and names are not
  unique). Browsing a board's pins reuses
  the cursor pagination since a board can hold many pins.

## 4. Domain model

Pure domain (no I/O):

```
data class Board(
    override val id: UUID,
    val author: User,
    val name: String,
    val description: String,
    val softDeletedAt: Instant? = null,
) : Identifiable
```

`Pin` carries `boards: List<Board>` (no default), mirroring its existing `tags: List<Tag>`.
The relation is persisted through a `pin_board` join table and a set-based diff in the pin
repository (mirroring the tag join), and it is loaded **active-only** so a recycled board never
appears among a pin's boards. `Board` carries no back-reference to its pins.

> **Amendment (2026-07-20):** an earlier draft stated the relation was "not a field on `Pin`".
> Reversed after reading the codebase: tags already live on `Pin` this way, and putting boards
> on `Pin` is what lets every `PinOutputDto` expose them without a separate load at each call
> site. The API contract is unchanged.

## 5. REST surface

All endpoints are `@Authenticated` and owner-scoped. Owner-scoping matches the pin precedent
exactly: a board owned by another user returns **403** (`BOARD_INSUFFICIENT_PERMISSIONS`), and
an unknown or recycled board on an active route returns **404** (`BOARD_DOES_NOT_EXIST`).

### Boards (active)

| Method | Path | Body | Result |
|---|---|---|---|
| POST | `/api/v1/boards` | `{name, description}` | `BoardOutputDto` |
| GET | `/api/v1/boards` | — | `BoardListOutputDto` (all active, sorted) |
| GET | `/api/v1/boards/{boardId}` | — | `BoardOutputDto` |
| PUT | `/api/v1/boards/{boardId}` | `{name, description}` | `BoardOutputDto` |
| DELETE | `/api/v1/boards/{boardId}` | — | 204, soft-deletes (to recycle bin) |
| GET | `/api/v1/boards/{boardId}/pins` | query: `cursor`, `pageSize`, `sort` | `PinListOutputDto` (active pins only) |

### Boards recycle bin (mirror of `/api/v1/pins/recycled`)

| Method | Path | Result |
|---|---|---|
| GET | `/api/v1/boards/recycled` | recycled boards |
| POST | `/api/v1/boards/recycled/{boardId}/restore` | restores the board |
| DELETE | `/api/v1/boards/recycled/{boardId}` | permanently deletes the board + its `pin_board` rows |
| DELETE | `/api/v1/boards/recycled` | empties the recycle bin |

### Membership (pin side)

| Method | Path | Body | Result |
|---|---|---|---|
| PUT | `/api/v1/pins/{pinId}/boards` | `{boardIds: [UUID]}` | `PinOutputDto` |

`PUT /pins/{pinId}/boards` **replaces** the pin's whole board set. Every id must reference an
**existing, active, owned** board; any unknown / recycled / non-owned id fails the whole
request (no partial set), via `BOARD_INVALID_MEMBERSHIP`.

### Output DTOs

- `BoardOutputDto = {id, name, description, pinCount}` where `pinCount` is the number of
  **active** pins currently in the board (a live aggregate, not stored).
- `BoardRefDto = {id, name}` — a lightweight reference (no description).
- `PinOutputDto` gains `boards: List<BoardRefDto>` alongside the existing `tags`.

## 6. Interaction rules & cascades

- `GET /boards/{boardId}/pins` returns only **active** pins; soft-deleted pins never appear.
- **Soft-delete of a board** keeps its `pin_board` rows. The board leaves `GET /boards` and
  its active routes (`GET /boards/{id}`, `.../pins`, `PUT /boards/{id}`) return 404 (invisible
  among active boards). It is reachable only through the recycle-bin routes. Restore brings it
  back with associations intact.
- **Permanent delete of a board** removes the board and its `pin_board` rows. No pin is
  touched (a pin may drop to zero boards, which is valid).
- **Permanent delete of a pin** also removes that pin's `pin_board` rows — extending the
  existing "permanently delete a pin and its tag associations" cleanup to boards.
- **Soft-delete / restore of a pin** does not touch its `pin_board` rows. While soft-deleted
  the pin simply does not appear in any active board listing.
- `pinCount` counts active pins only, consistent with what `.../pins` returns.

## 7. Architecture (hexagonal placement)

Follows the existing pin/tag/recycle-bin structure; each unit has a single responsibility.

- **api-domain**: `Board` entity; `Pin` gains `boards: List<Board>`; `BoardRepositoryInterface`
  (save, find-active-by-id, find-all-active-for-user, soft-delete, restore, permanently-delete,
  find-recycled-for-user, permanently-delete-all-recycled, count-active-pins). Extend
  `PinRepositoryInterface` with `findActivePinsForBoard(...)` (paginated); `savePin` also
  persists the pin's boards, and `permanentlyDeletePin` also clears its `pin_board` rows.
- **api-usecases** (depend on domain only): `BoardCreator`, `BoardUpdater`, `BoardGetter`
  (detail + active list), `BoardPinLister` (a board's active pins, paginated/sorted),
  `PinBoardSetter` (mirror of `PinTagger`), `BoardRecycleBin` (mirror of `PinRecycleBin`).
  New domain-specific exceptions (see §8).
- **api-persistence-sqlite**: `BoardModel` + `BoardModelMapper`; the `pin_board` join;
  Ebean repository implementations; migration (next version, **1.7**).
- **api-presentation-quarkus**: `BoardController` + `BoardRecycleBinController`; input DTOs
  (`BoardInputDto`, `PinBoardsInputDto`) and output DTOs (`BoardOutputDto`,
  `BoardListOutputDto`, `BoardRefDto`); `PinController.setBoards` for the membership PUT;
  error-mapper arms for the new codes.
- **api-application**: wire the new repositories; integration tests.

## 8. Errors

Mirror the existing pin exception/`ErrorCode` conventions (per-use-case exception hierarchy on
`BaseError`, shared `ErrorCode` values), mapped by the existing `BaseErrorMapper`:

- `BOARD_DOES_NOT_EXIST` → 404 (unknown or recycled board on an active route).
- `BOARD_INSUFFICIENT_PERMISSIONS` → 403 (a board owned by another user; matches the pin
  non-owner behaviour, which returns 403).
- `BOARD_NOT_SOFT_DELETED` → 409 (restore or permanently delete a board that is not recycled).
- `BOARD_ALREADY_SOFT_DELETED` → 409 (soft-delete a board that is already recycled).
- `BOARD_INVALID_MEMBERSHIP` → 400 (a `boardIds` entry is unknown / recycled / non-owned in
  `PUT /pins/{pinId}/boards`).

The 409 codes mirror `PIN_NOT_SOFT_DELETED` / `PIN_ALREADY_SOFT_DELETED` (both `CONFLICT`).

## 9. Persistence & migration

- Table `boards`: `id`, `author_id` (FK users), `name`, `description`, `soft_deleted_at`
  (nullable). `author_id` is FK-indexed like the other authored tables; no composite
  `(author_id, soft_deleted_at)` index is generated (Ebean follows the `pins`/`tags` precedent,
  and a user's board set is small enough to filter in memory).
- Join table `pin_board_model` (Ebean's default name; the join model has no `@Table`, mirroring
  `pin_tag_model`): `pin_id` (FK pins), `board_id` (FK boards). No composite primary key (follows
  `pin_tag_model`); the `savePinBoards` set-diff prevents duplicate rows. Cascade rules are
  enforced in the repository layer (matching how the
  pin↔tag cleanup is done today), not relied upon from DB-level cascades unless the existing
  tag join already does so — follow the tag-join precedent.
- Ebean migration **1.7** (last shipped is 1.6). Generated via
  `./gradlew :api-persistence-sqlite:generateDbMigration`.

## 10. Testing strategy

Strict TDD, 100% branch coverage per package, failing test first. Order per AGENTS.md:
integration (REST Assured) → use-case unit (MockK) → repository (Ebean).

Both sides of every conditional, in particular:

- Membership set-based replace: add, remove, no-op, and the all-or-nothing failure on an
  invalid `boardId`.
- Recycle-bin cascades: soft-delete keeps `pin_board`; restore is exact; permanent delete
  clears `pin_board`; empty clears all recycled.
- Owner-scoping on every route (owned vs non-owned → the pin precedent's status).
- `pinCount` counts active pins only (excludes soft-deleted pins).
- `GET /boards/{id}/pins` excludes soft-deleted pins and honours sort + cursor.
- Board detail/list/PUT on a recycled board → 404.
- Permanent delete of a pin clears its `pin_board` rows.

## 11. Risks / open points

- **`pinCount` cost.** A per-board aggregate on `GET /boards` could be N+1 if done naively.
  Resolve with a single grouped count query in the repository; the plan should call this out.
- **Set-based membership races.** Two concurrent `PUT /pins/{id}/boards` last-writer-wins, as
  with tags today. Acceptable; no locking in scope.
- **Migration 1.7 on existing data.** Purely additive (new tables); no backfill needed since
  existing pins simply start in zero boards.
