# CORS configuration

Date: 2026-07-21
Status: approved design, pending implementation
Depends on: session-token authentication (the client auth model must be fixed before CORS can be
scoped). No dependency on pins/boards/images.

## 1. Goal

Let browser clients (the web SPA, later the browser extension) call the API from another origin.
Today no `quarkus.http.cors*` entry exists, so Quarkus permits only same-origin requests and every
cross-origin call from a browser is blocked. This is the next P1 "client ergonomics" item in
`docs/backlog.md`, unblocked now that auth is fixed (Bearer, no cookies).

## 2. Scope

**In scope:**

- Enable the Quarkus CORS filter and configure allowed origins, methods, and request headers.
- Drive the allowed origins from a **project-namespaced** property (`api.cors.origins`, declared in
  `ApiConfig`) with a dev default, overridable in prod via the `API_CORS_ORIGINS` environment
  variable, so operators never touch the framework-namespaced `QUARKUS_HTTP_CORS_ORIGINS`.
  All publicly configurable knobs live under the `api.` prefix by project convention.
- Integration tests proving the CORS contract from a browser's point of view.

**Out of scope (deferred):**

- **Browser-extension origins** (`chrome-extension://<id>`, `moz-extension://<id>`). The extension
  does not exist yet and has no stable ID; wiring a broad regex now would allow any installed
  extension. Recorded as a follow-up backlog item (decision B1).
- **Credentialed requests** (cookies / `credentials: 'include'`). Auth is Bearer via the
  `Authorization` header only and will stay so, so `access-control-allow-credentials` is left off
  (defaults to `false`).
- **`exposed-headers`.** The create/202 endpoints set `Location`, but their response body already
  carries the created entity (with its `id`), so no non-safelisted response header needs to be
  readable from JS. Trivial to add later if a client needs it.

## 3. Design

### 3.1 Typed config (`ApiConfig`)

`ApiConfig` (`@ConfigMapping(prefix = "api")`) is the typed view of every `api.*` property. The CORS
origin is declared there so the public knob stays under the `api.` prefix **and** is a mapped
property (avoiding SmallRye's unknown-property validation, which would otherwise reject an unmapped
`api.cors.*` sitting under `ApiConfig`'s strict prefix):

```kotlin
@ConfigMapping(prefix = "api", namingStrategy = ConfigMapping.NamingStrategy.SNAKE_CASE)
interface ApiConfig {
    // ... host(), remoteHost(), port(), basePath(), baseUrl() unchanged ...
    fun cors(): Cors

    interface Cors {
        /** Forwarded verbatim to `quarkus.http.cors.origins` via `${api.cors.origins}`. */
        fun origins(): String
    }
}
```

`cors().origins()` (→ `api.cors.origins`) is populated and validated at startup. It is not read by
application code: Quarkus's built-in CORS filter reads the framework property `quarkus.http.cors.origins`
directly, and the filter cannot be fed from `ApiConfig`. The typed member's role is to keep the public
config surface complete and validated, not to be consumed. Abstract interface methods carry no
branches, so this adds nothing to the coverage surface.

### 3.2 Configuration

Added to `api-application/src/main/resources/application.properties`:

```properties
# CORS: browser clients (SPA, later the extension) hit the API cross-origin.
# Bearer auth via the Authorization header only (no cookies), so credentials stay off.
quarkus.http.cors.enabled=true
api.cors.origins=http://localhost:5173
quarkus.http.cors.origins=${api.cors.origins}
quarkus.http.cors.methods=GET,POST,PUT,DELETE
quarkus.http.cors.headers=Authorization,Content-Type
quarkus.http.cors.access-control-max-age=PT24H
```

Rationale per line:

- **`api.cors.origins` + `${...}` indirection** mirrors the existing `api.host` →
  `quarkus.http.host=${api.host}` idiom (a project property carries the default; the framework
  property references it). The default `http://localhost:5173` is the typical Vite/SPA dev origin.
  Prod sets `API_CORS_ORIGINS` (MicroProfile relaxed mapping of `api.cors.origins`). The property is
  under `api.` because publicly configurable knobs live there by convention (§3.1), and it is mapped
  in `ApiConfig` so it passes strict unknown-property validation.
- **`methods=GET,POST,PUT,DELETE`** are the only verbs the controllers expose (no PATCH). The CORS
  filter answers the `OPTIONS` preflight itself.
- **`headers=Authorization,Content-Type`**: neither is CORS-safelisted for our use. JSON writes send
  `Content-Type: application/json` (not one of the three safelisted content types), and the Bearer
  token rides in `Authorization`; without these listed, every authenticated write would fail
  preflight. Listing them explicitly turns Quarkus's default header-mirroring into a whitelist.
- **`access-control-max-age=PT24H`** caches preflight results so the browser skips the `OPTIONS`
  round-trip on repeat calls. Optimization only; ISO-8601 for consistency with the rest of the file.
- **No `access-control-allow-credentials`** → defaults `false`; no cookies in play.

### 3.3 Tests (TDD first)

New `CorsIntegrationTest` in `api-application` (REST Assured), the project's first testing tier.
A deterministic allowed origin is pinned in `api-application/src/test/resources/application.properties`
(`api.cors.origins=https://app.test`) so tests are decoupled from the dev default.

| Test | Assertion |
|------|-----------|
| Preflight `OPTIONS` from the allowed origin | response carries `Access-Control-Allow-Origin` = that origin; `Access-Control-Allow-Methods` includes the requested method; `Access-Control-Allow-Headers` includes `authorization` |
| Preflight `OPTIONS` from a disallowed origin | response carries **no** `Access-Control-Allow-Origin` header (a browser would block the call) |
| Actual `GET` carrying the allowed `Origin` | response carries `Access-Control-Allow-Origin` = that origin |

Existing integration tests send no `Origin` header (same-origin), so they are unaffected.

### 3.4 Coverage

The only Kotlin change is two abstract members on `ApiConfig` (`cors()`, `Cors.origins()`), which
carry no branches, so per-package branch coverage stays 100% trivially. Behavioural proof (that the
mapping binds and the filter enforces the policy) comes from the integration tests above.
