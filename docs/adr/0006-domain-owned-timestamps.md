# 0006. Domain-owned timestamps and a single soft-delete mechanism

Status: Partially superseded by `0007-single-representation-soft-delete.md` (decision 4). The eleven
other decisions stand. `0007` also records two factual errors in the Context section below, both about
what the automatic soft-delete predicate covers.
Date: 2026-07-29

## Context

The invariant "domain data is stamped by use cases, never invented by adapters" was decided on
2026-07-23 and is recorded in `agents/project.md`. The timestamps refactor that established it
deliberately left two residues open in `docs/backlog.md`: `softDeletedAt` is still stamped inside the
persistence adapter, and soft delete no longer bumps `updatedAt`. A third backlog item, the
`findCurrentPasswordHash` tie-breaker, was filed separately as a latent fragility on a
security-critical read.

Reading the code to scope those three items showed they are one defect with three faces, and that the
defect is wider than the backlog recorded. Three columns generated by Ebean are read to decide
something the business owns:

| Generated column | What it decides | Site |
|---|---|---|
| `users.when_modified` | permanent deletion of a tombstoned account | `UserRepository.kt:81` |
| `tasks.when_modified` | deletion of a terminal task | `EbeanTaskQueue.kt:229` |
| `user_password_hashes.when_created` | which password hash is the current one | `UserPasswordHashRepository.kt:35` |

`@WhenModified` is rewritten on every write to the row. A retention rule driven by it restarts its
countdown whenever anything touches the row, with nobody deciding it. For account deletion that is a
retention promise governed by a technical timestamp that moves on its own.

Every other occurrence of `when_created` / `when_modified` is dead: nothing in production reads
`tags.when_modified`, `session_tokens.*`, `user_data_exports.*`, `tasks.when_created`, or
`user_password_hashes.when_modified` (verified with `rg "whenCreated|whenModified"` over
`api-persistence-sqlite/src/main`, which returns only the three sites above plus the declarations).

A second finding: the codebase carries two soft-delete mechanisms. `UserModel` uses Ebean's
`@SoftDelete deleted` boolean, whose filtering Ebean applies automatically to every table in the FROM
and JOIN clauses (ebean.io/docs/features/softdelete). `PinModel` and `BoardModel` carry a bare
`softDeletedAt: Instant?` and filter by hand. Four direct `QUserModel()` accesses and 26 `.author.` /
`.user.` joins currently depend on the automatic filtering without saying so, including
`SessionTokenRepository.kt:22`, which is what stops a tombstoned account from obtaining a session.

The same documentation states that the `@SoftDelete` property must be of boolean type, so a nullable
instant cannot carry the annotation.

## Decision

1. **Every business instant is stamped by a use case, and the persistence adapter never reads a
   clock.** The four soft-delete transitions (`softDeletePin`, `restorePin`, `softDeleteBoard`,
   `restoreBoard`) and `markPendingDeletion` take the instant as a parameter rather than calling
   `Instant.now()`. A Konsist test forbids `Instant.now()` in `api-persistence-sqlite`, which is the
   assertion that makes the invariant true rather than intended. There are exactly two occurrences to
   remove (`PinRepository.kt:195`, `BoardRepository.kt:50`).

2. **`updatedAt` means any modification, including recycling and restoration.** The alternative was to
   define it as "last content change" and let `deletedAt` carry the state separately. Rejected: it
   forces an arbitration of which fields and which state transitions move `updatedAt`, and that
   arbitration has to be redone for every field added afterwards. One rule that needs no exception
   list beats a narrower rule that needs one.

3. **The transitions take the instant; they do not route through `savePin` / `saveBoard`.** Passing
   the updated entity to the existing save method would have shrunk the repository interface, but
   `savePin` resynchronises tags and boards on every call (`PinRepository.kt:76-81`), so a recycling
   would rewrite join rows it has no reason to touch, and a `Pin` held in memory with an incomplete
   join list would silently erase them. A recycling that loses tags is a silent data-loss path, traded
   for an interface with four fewer methods. Not worth it.

4. **One soft-delete mechanism: Ebean's `@SoftDelete`, generalised, with the boolean derived by the
   mapper.** `PinModel` and `BoardModel` gain `@SoftDelete deleted: Boolean`; `UserModel` keeps it. The
   domain keeps a single field, `softDeletedAt: Instant?`, and the mapper derives `deleted =
   softDeletedAt != null` on the way out. The two columns cannot diverge because one source feeds
   both, and deriving a boolean from a value the use case supplied is not the adapter inventing data:
   no clock is involved.

   The opposite alignment was considered, dropping `@SoftDelete` and filtering by hand everywhere as
   `Pin` and `Board` already do. It was rejected on measurement: the automatic predicate covers the 26
   joins as well as the four direct accesses, and no helper can reach the joins, since they navigate
   an association from `QPinModel` or `QTagModel` rather than constructing a `QUserModel`. Choosing it
   would convert an automatic guard into human discipline on the authentication path, where a missed
   filter opens a session for a deleted account.

5. **`User.softDeleted: Boolean` becomes `User.softDeletedAt: Instant?` in the domain**, aligned with
   `Pin` and `Board`. The retention sweep reads that instant instead of `when_modified`, so it
   measures what it claims to measure.

6. **`AuditedBaseModel` is deleted, and `@WhenCreated` / `@WhenModified` are forbidden in the
   persistence layer** by a second Konsist test. A test with an exemption list is an inventory, not a
   guard, so the ban requires zero remaining occurrences, which is why all six affected models are in
   scope and not only the three with a read defect.

7. **A column is promoted to a named domain fact when it is read, and deleted when it is not.**
   Promoting every audit column to a generic `createdAt` / `updatedAt` pair would reproduce the
   original error one layer up: the defect was never that the columns were generated, it was that a
   generic timestamp stood in for a fact nobody had named. `UserDataExport` already carries
   `requestedAt`; `HashedPassword` is immutable and can have no update instant; account retention
   needs "when was this tombstoned", not "when was this row last written"; task retention needs "when
   did this enter a terminal state". Accordingly `User` receives `softDeletedAt`, `Task` receives
   `terminalStateAt`, `HashedPassword` receives `createdAt`, `SessionToken` receives `createdAt`
   (kept for incident debugging), and `Tag`, `Pin`, `Board` and `UserDataExport` receive nothing new.
   Seven dead columns are dropped.

8. **The current password stays an ordered read, made deterministic by a unique constraint and a rate
   limit, rather than becoming an explicit marker.** A `(user_id, created_at)` unique constraint turns
   a nondeterministic ordering into a refused insert, and a configurable interval defaulting to 30
   seconds, enforced in the use case, keeps the constraint out of reach in normal use. The considered
   alternative was to make "current" explicit in the repository contract (`replaceCurrentPasswordHash`
   plus a partial unique index), which would have removed the tie-break by construction; it was not
   retained because it decides field-by-field what the ordering already expresses, and the constraint
   plus interval closes the same hole with a smaller contract change.

9. **A residual unique-constraint violation is a 409, not a 500.** Two concurrent requests from the
   same user can pass the interval check together and attempt two inserts in the same tick. The window
   is narrow, but it is exactly what the constraint exists to catch, so it gets a named outcome:
   `PASSWORD_CHANGE_COLLISION`, mapped to 409, with the Ebean exception translated into a domain error
   at the adapter. The rate-limit refusal is `PASSWORD_CHANGED_TOO_SOON`, mapped to 429 like
   `EXPORT_TOO_SOON`.

10. **The rate limit counts successful changes, not attempts, and does not protect against brute
    force.** It reads the current hash's `createdAt`, so a failed attempt writes nothing and costs the
    caller nothing. `changePassword` verifies the current password and is therefore a password oracle,
    as is `POST /api/v1/sessions`; limiting authentication attempts is a distinct security feature
    with its own state and its own specification, and it goes to the backlog. Naming this here is the
    point: "there is a rate limit on password change" would otherwise be read later as "brute force is
    handled".

11. **The export archive does not change `formatVersion`.** Decision 2 changes the meaning of
    `updatedAt` in `pins.jsonl` and `boards.jsonl` without changing the archive's shape. Version 1
    never promised "last content change" (it was accidental behaviour, not a specified one), no
    consumer exists since import is not written, and bumping a version signals a change to nobody
    while forcing the future importer to distinguish two byte-identical formats. The semantics are
    written down here and in the spec instead.

12. **No backfill.** Nothing is deployed anywhere, so there are no rows whose contradiction would
    matter.

## Consequences

- The three retention and authentication decisions listed in the context stop depending on a column
  Ebean rewrites. Account retention measures time since tombstoning, task retention measures time
  since entering a terminal state.
- One soft-delete mechanism remains in the codebase instead of two, and it is the one with automatic
  filtering, so the 26 joins and the four direct accesses keep their guard without any of them being
  touched.
- The generalisation has a loud cost: with `@SoftDelete` on pins and boards, a normal query excludes
  deleted rows, so the six recycle-bin queries that filter `.softDeletedAt.isNotNull`
  (`PinRepository.kt:216, 237, 255`, `BoardRepository.kt:45, 68`) return empty until they add
  `setIncludeSoftDeletes()`. Eight `.isNull` filters become redundant, and cursor pagination on
  `softDeletedAt` (`PinModelSortStrategy.kt:123-141`) is affected. Existing integration tests fail
  immediately if this is missed, so it is visible work rather than a silent bug.
- Two new `ErrorCode` values enter `BaseErrorMapper.statusFor`, which is a public contract change: the
  password-change endpoint gains a 409 and a 429 it did not have.
- `markPendingDeletion` stops calling `database.delete()` and writes the mapped model instead. Whether
  Ebean honours a `@SoftDelete` property written by hand rather than through `database.delete()` is
  the principal technical risk of this work and is proven by a test before anything is built on it.
- Two Konsist tests encode the invariants, so the debt cannot return silently.
- The work is delivered as three sequential blocks in three sessions, ordered by dependency: soft
  delete first, then the end of `AuditedBaseModel`, then the current-password work. Account retention
  cannot stop reading `when_modified` before `softDeletedAt` exists, and `UserPasswordHashModel` only
  leaves `AuditedBaseModel` in the second block.
